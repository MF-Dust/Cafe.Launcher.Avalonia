# ADR-062：自更新独立来源证明方案待裁决

- 状态：提案，待维护者裁决；不替代 ADR-037，不代表风险已接受或已修复
- 日期：2026-11-15
- 相关：[ADR-037](ADR-037-Windows自更新走独立helper且以SHA256SUMS为信任锚.md)、[审计台账 AUD-SEC-010](../../../CODEBASE_AUDIT.md#开放发现)

## 需要决定什么

是否及如何让客户端验证独立于下载镜像的发布者身份。当前 SHA256SUMS 仍是内容完整性依据，但不能证明发布者身份；发现、证据与关闭条件只在审计台账维护。

## 候选方案

| 方案 | 收益 | 发布与客户端成本 |
| --- | --- | --- |
| 验证 GitHub artifact attestation / Sigstore bundle | 复用现有 CI 来源证明，不必长期保存额外签名私钥 | 明确固定的仓库、工作流身份和签发者，验证证书链、签名、包摘要与证明策略；决定离线 bundle、信任根更新与网络不可用行为 |
| 固定公钥验证签名 SHA256SUMS | 清单与包可由任意镜像分发；客户端可离线验签 | 选择成熟格式与实现；管理私钥、CI 签名权限、轮换与撤销；清单必须绑定版本和资产名，不能仅签无版本摘要 |
| 暂维持现状 | 无兼容性迁移成本 | 不解决镜像同时替换清单与包；若选此项，需明确接受风险，而不是把 URL 收紧或平台代码签名当成同一问题的修复 |

## 裁决前必须回答

1. 签名／证明的信任主体、格式、验证依赖和密钥／信任根管理由谁维护？
2. 发布流水线先双发证明，再发布带验证能力的客户端；旧客户端的暴露窗口如何公告和结束？旧客户端不会因发布新证明而自动获得保护。
3. 新客户端何时开始强制验证？缺失、过期、错误身份、未知密钥和验证失败必须拒绝应用内执行，不得静默降级为只验哈希。
4. 如何绑定版本、资产名与摘要，并延续现有禁止可信降级的契约？离线、密钥轮换与撤销如何处理？
5. 镜像是否需要额外同步 bundle／签名资产；证明下载失败的备用路径如何测试？

## 验收门槛

- 同时篡改镜像清单与包时拒绝执行；正常安装版、便携版与 GitHub 备用下载仍可更新。
- 缺失／无效签名、错误发布身份、错误版本／资产摘要、旧签名重放与轮换边界均有回归用例。
- 发布侧产物、主程序首次验证与 helper 执行前验证具有一致的失败闭合策略，保留当前 SHA-256 和路径边界。

本提案不引入签名库、生成密钥或修改发布配置。维护者选择方案并明确迁移策略后再实施。
